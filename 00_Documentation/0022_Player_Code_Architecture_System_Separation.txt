WARDOGZ II DOCUMENTATION 0022 - Player Code Architecture / System
Separation

Date: 2026-08-11

============================================================ TITLE
============================================================

0022_Player_Code_Architecture_System_Separation

============================================================ OBJECTIVE
============================================================

Reorganize the growing player system into separate source and header
files without removing or replacing the player systems completed in
Documentation 0013 through 0017.

The player code previously placed most player behavior inside:

src.c include.h

The system is now separated by responsibility so future combat, combo,
and move systems can grow without turning player.c into one very large
file.

============================================================ IMPORTANT
DOCUMENTATION RULE
============================================================

-   Walking animation

-   Basic attacks
-   Attack movement lock
-   Attack hitboxes
-   Enemy damage
-   Enemy knockback
-   Punk sprite / idle animation

remain part of the project.

============================================================ PLAYER.C /
PLAYER.H ============================================================

Files:

src.c include.h

Purpose:

These remain the CORE player files.

player.h contains the main Player structure and shared player
definitions required by the separated player systems.

The Player structure continues to store the player’s shared state,
including:

-   Position / rectangle
-   Speed
-   Idle animation state
-   Walking animation state
-   Attack animation state
-   Current attack
-   isAttacking
-   isWalking
-   Facing direction
-   Player textures

player.c handles the core player initialization and cleanup, including
loading and unloading the player textures.

Purpose:

Handles visual rendering of the player.

This section contains:

-   Attack texture selection

============================================================
UPDATEPLAYER CONNECTION
============================================================

The main game loop can continue using:

UpdatePlayer(…)

The internal player systems are separated, but main.c does not need to
manually control every movement and attack subsystem.

This keeps main.c focused on the high-level game loop.

============================================================ MAIN.C ROLE
============================================================

main.c remains responsible for high-level game flow.

Current important flow:

UpdatePlayer(…)

UpdateEnemyHit(…)

DrawEnemy(…)

DrawPlayer(…)

The detailed player behavior is handled by the player subsystem files
instead of being written directly inside main.c.

============================================================ WHY THIS
SEPARATION IS IMPORTANT
============================================================

The player combat system is expected to grow.

Keeping all future moves inside one player.c would make the file
increasingly difficult to read, debug, and maintain.

The separated structure allows each area to grow independently:

player.c Core player data / initialization / cleanup

player_move.c Movement / facing / idle / walking / boundaries

player_attack.c Basic attacks / hitboxes / future combos and command
moves

player_draw.c Player sprite rendering / scaling / mirroring / debug
drawing

This creates a cleaner foundation for a larger beat-’em-up combat system
and future Tekken-style move expansion.
